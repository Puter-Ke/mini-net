# 压测指南（echo_bench）

> 这份文档讲清楚三件事：**怎么压**、**每个参数是什么意思**、**测出来的数字该怎么看（以及哪些数字不能信）**。

## 1. 为什么自己写一个压测客户端

市面上的压测工具都能用，但对这个项目来说各有各的别扭：

| 工具 | 优点 | 为什么这里不合适 |
|---|---|---|
| `ab`（Apache Bench） | 系统自带、一条命令就出结果 | 一条连接一个请求，测不出**长连接复用**的吞吐；也不支持 HTTP 流水线 |
| `wrk` | 性能极强、能压出很高 QPS | 只认 HTTP，回显协议测不了；参数固定，想改测量方式得改 C 代码 |
| `scripts/bench_quick.py` | 改动最方便 | Python 的 asyncio 本身开销大，几千并发时**瓶颈先出现在客户端**，数字会明显偏低 |

自己写的好处不只是"能测"：`QPS`、`P50`、`P99` 这几个数字是**你算出来的**，
面试官追问"这个 29k QPS 怎么来的、延迟是从哪一刻算到哪一刻"，你能一句句讲清楚。

## 2. 编译

`bench/CMakeLists.txt` 里已经加好了目标，跟着主工程一起编就行：

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ls -l build/echo_bench
```

想单独编（比如临时改两行试试）：

```bash
g++ -std=c++17 -O2 -pthread bench/echo_bench.cc -o echo_bench
```

> 注意：压测**一定要用 Release**。Debug 版本（`-O0 -g`）编出来的服务端，
> QPS 可能只有 Release 的十分之一，测出来的数字没有意义。

先看帮助，所有参数的说明都在里面：

```bash
./build/echo_bench --help
```

## 3. 两种模式

### echo 模式（默认）——打回显协议

服务端 M1 的回显逻辑是"收到什么就原样发回什么"。
客户端每条连接循环：发 `--size` 个字节 → 收到同样多的字节 → 再发下一个。

```bash
# 1000 条连接，每条连接发 1000 个 64 字节的消息
./build/echo_bench --host 127.0.0.1 --port 8080 --conns 1000 --requests 1000 --size 64
```

如果服务端回显的内容和发出去的不一样（少发、串包、乱码），
客户端会立刻报错并给出"第几个字节开始对不上"，方便你定位。
不想付这个校验开销（校验要逐字节比较）可以加 `--no-verify`，
但那样就只剩下"长度对不对"这一条检查了。

### http 模式——打真实的 HTTP 接口

```bash
# 健康检查接口（最干净的一条路径，适合测服务框架本身的极限）
./build/echo_bench --mode http --path /healthz --conns 1000 --requests 1000

# 短链创建：注意用 %d 让每条连接发不同的 URL，否则服务端会去重返回同一个短码，
# 测到的是"命中已有记录"的读路径，而不是真正的"插入"路径
./build/echo_bench --mode http --method POST --path /api/shorten \
                   --body '{"url":"https://example.com/bench/%d"}' --conns 200

# 短链跳转：先把上面创建的短码填进 --path，跳转返回 302，要改期望状态码
./build/echo_bench --mode http --path /aB3cD --expect-status 302 --conns 1000

# 查统计
./build/echo_bench --mode http --path /api/stats/aB3cD --conns 200
```

HTTP 模式下客户端会自己解析响应（状态行、响应头、`Content-Length`、body），
所以能准确地在"一个响应收完"的那一刻记一次延迟。
如果服务端返回了 `chunked` 编码或者不带 `Content-Length`，客户端会直接报错——
因为这两种情况它没法判断响应到哪里结束；接口契约要求服务端始终带 `Content-Length`。

## 4. 参数都是什么意思

| 参数 | 默认 | 说明（大白话） |
|---|---|---|
| `--host` / `--port` | 127.0.0.1 / 8080 | 要打哪个服务。只支持 IPv4 |
| `--conns N` | 100 | **同时开多少条连接**。这就是"多少人同时在线" |
| `--requests N` | 1000 | **每条连接发多少个请求**。总量 = conns × requests |
| `--duration 秒` | 0 | 改成"按时间压"：压满这么多秒就停。设了它 `--requests` 就不起作用了 |
| `--pipeline N` | 1 | **一次在途多少个请求**（见下面第 6 节的解释） |
| `--size N` | 64 | echo 模式每条消息多少字节 |
| `--mode` | echo | `echo` 或 `http` |
| `--path` | /healthz | http 模式请求哪个路径 |
| `--method` | 自动 | `/api/shorten` 自动用 POST，其他用 GET |
| `--body` | 自动 | POST 的请求体，支持 `%d` 占位符（会替换成连接序号） |
| `--expect-status` | 自动 | 期望的状态码，可写多个如 `302,200`。不符的响应会被单独统计，不算"成功" |
| `--timeout-ms` | 5000 | 一条连接多久没动静就算它失败了 |
| `--source-ip-count N` | 1 | 用几个源地址（见下面第 8 节的"端口耗尽"） |
| `--nodelay` | 关 | 打开 TCP_NODELAY，即关掉 Nagle 算法（做对照实验用） |
| `--label` | 空 | 报告标题，比如 `baseline-4thread`，方便区分不同轮次 |
| `--json 文件` | 空 | 额外写一份 JSON 结果，方便 CI 里比较两轮的数字 |

## 5. 结果怎么看

```
 QPS（成功）       : 292,311
 延迟 P50/P90/P99/P999 (微秒): 12 / 30 / 95 / 320
 进程 CPU 时间     : 用户 5.20 s + 系统 2.10 s = 7.30 s（占单核 213%）
 峰值内存 RSS      : 18.4 MB
```

- **QPS（吞吐）**：每秒处理完多少个请求。注意报告里给了两个：
  `QPS（成功）` 只算状态码符合预期的；`QPS（总完成）` 把返回了非预期状态码的也算上。
  两个数字差得远，说明服务端在返回错误，先把错误查清楚再看性能。
- **P50 / P90 / P99 / P999**：把这一轮所有请求的耗时从小到大排队，
  排在第 50% / 90% / 99% / 99.9% 位置的那个值。
  单位是**微秒**（1 毫秒 = 1000 微秒）。
  - P50 = 12 微秒：一半的请求在 12 微秒内返回，这是"平常的速度"。
  - P99 = 95 微秒：最慢的那 1% 请求，比 95 微秒还慢。
  - **为什么必须看 P99 而不是只看平均值**：平均值会把偶发的卡顿抹平。
    想象 100 个人排队，99 个人 1 秒就办完、1 个人等了 100 秒，
    平均下来是"每人 2 秒"，看着还行，但那个等 100 秒的人体验是灾难。
    P99 就是用来抓这种"少数人的糟糕体验"的。
  - P999（99.9%）比 P99 更极端，通常用来排查"每隔一阵就抖一下"的问题
    （比如内存池扩容、定时器批量触发、日志刷盘）。
- **进程 CPU 时间**：压测客户端自己用了多少 CPU。
  **这个数字非常重要**：如果它接近"占单核 100%"，说明客户端自己已经跑满了，
  你测到的其实是**客户端的上限**，不是服务端的上限——报告里会专门打一条 `[注意]` 提醒。
- **峰值内存 RSS**：客户端进程用过的最大物理内存。客户端自身应该很小（几十 MB）；
  如果这里涨到几百 MB 甚至 GB，先查客户端（比如延迟样本堆太多）。
- **建立连接耗时**：所有连接从开始建到全部就绪花了多久。
  这段时间**不参与** QPS 计算——测量窗口是"所有连接都准备好之后"才开始的，
  不然 1000 条连接一条条建的过程会被算进耗时里，把 QPS 压低。

## 6. pipeline 是什么，什么时候用

不开 pipeline（`--pipeline 1`，默认）时，每条连接是"发一个 → 等响应 → 再发下一个"。
一个请求的耗时里，有很大一块是"在网络上跑一个来回"的时间（RTT）。

开了 `--pipeline 16`，客户端会**一口气先发 16 个请求**，
然后一边收响应一边补发新的，始终让 16 个请求在路上。

- 好处：把 RTT 的影响摊薄，同样的连接数能压出更高的吞吐，更接近"服务端到底能处理多快"。
- 代价：**延迟数字会变大**。因为第 16 个请求要排队等前面 15 个先被处理，
  它测到的延迟里包含了排队时间。这是流水线的固有特性，不是 bug。

所以：**要测吞吐就用 pipeline，要测响应延迟就用 pipeline=1**，两者不要混着比。

## 7. 同机压测为什么会失真

这是最重要的一节。`echo_bench` 和服务端很可能跑在**同一台机器**上，这时候：

1. **抢 CPU**：服务端 4 个线程 + 客户端 1 个线程，如果机器只有 4 个核，
   它们会互相抢。服务端本来能跑满 4 核，现在只能拿到 3 核多，QPS 自然低。
2. **抢内存带宽和缓存**：两边都在疯狂读写内存，CPU 的三级缓存会被互相挤掉，
   表现出来就是"什么都没改，QPS 却忽高忽低"。
3. **网络是假的**：回环（127.0.0.1）不经过网卡，没有真实网络的延迟、抖动和丢包。
   所以同机测出来的 P99 往往**比真实网络环境好看得多**。
4. **客户端可能先到极限**：客户端单线程要处理上千条连接的收发和统计，
   它先跑到 100% CPU 的情况很常见。看报告里的 `进程 CPU 时间`，
   超过单核 85% 就会有 `[注意]` 提示。

**怎么减少失真**：

- 正式对比数据用**两台机器**（笔记本 + 台式机 / 云主机都行），千兆网直连。
- 只有一台机器时：把服务端绑到几个核、客户端绑到另外的核（`taskset`），别让它们抢：
  ```bash
  taskset -c 0-3 ./build/mini_net_server 8080     # 服务端用 0~3 号核
  taskset -c 4   ./build/echo_bench --conns 1000  # 客户端独占 4 号核
  ```
- 客户端单核不够时，**同时跑多个客户端进程**（每个进程用不同的 `--source-ip-count`
  或者不同的连接数），把它们的结果加在一起：
  ```bash
  ./build/echo_bench --conns 500 --requests 2000 --label c1 &
  ./build/echo_bench --conns 500 --requests 2000 --label c2 &
  wait
  ```
- 无论怎么测，**都把环境写进 docs/RESULTS.md**：CPU 型号、核数、是不是同机、
  服务端几个线程、编译选项。少了这些，数字就没法对比。

## 8. 常见问题

### 报错"本地端口耗尽" / `无法分配请求的地址` / `地址已被使用`

这是同机压测**最常见的坑**，而且特别容易被误判成"服务端崩了"。

原因：客户端每开一条连接，就要占用一个"本地临时端口"。
Linux 默认只给了两万多个（`/proc/sys/net/ipv4/ip_local_port_range`），
而且是按"（源地址, 源端口, 目标地址, 目标端口）"这四样东西唯一确定的。
你打的是同一个服务端，那源地址和源端口就成了唯一的变量——**源端口用完就没了**。

`echo_bench` 在启动时会先把这笔账算给你看，不够就提前警告。
真遇到了，四种办法任选：

1. **多源地址**（最推荐，不用改系统配置）：回环网段 `127.0.0.0/8` 整段都是本机地址，
   每个源地址都有一份独立的端口空间。
   ```bash
   ./build/echo_bench --conns 2000 --source-ip-count 16   # 用 127.0.0.1 ~ 127.0.0.16
   ```
2. 扩大端口范围：`sudo sysctl -w net.ipv4.ip_local_port_range="1024 65535"`
3. 复用 TIME_WAIT 的端口：`sudo sysctl -w net.ipv4.tcp_tw_reuse=1`
4. 老实减少并发：`--conns` 调到可用端口数以内

> 顺带一提：`SO_REUSEPORT` 解决不了这个问题。它允许"多个 socket 绑同一个本地端口"，
> 但**同一个四元组的连接不可能存在两条**，所以对"打同一个服务端"这个场景没用。
> 它真正的用途是让多个压测进程能共用端口、以及方便复用 TIME_WAIT 的端口。

### 报错"连接被拒绝"

服务端没起来。先跑 `./build/mini_net_server 8080`，
或者检查 `--host` / `--port` 写错了没有。

### 压测一开始，服务端日志里多了一条"连上又马上断开"的连接

这是正常的：客户端在正式开压之前会先拿一条普通连接**探路**
（确认服务端在监听、地址端口没写错），探完立刻关掉。

副作用是服务端的 `total_connections` 会多 1。
如果你在用 `/metrics` 做精确断言（比如"连接数必须恰好等于 1000"），
把这个探路连接算进去，或者干脆在断言时留 1 的余量。

### 报错"回显内容不对"

服务端的回显逻辑有 bug（回的内容和收到的对不上）。
这是**压测工具帮你抓到的真 bug**，比性能数字有价值，记进 `docs/PITFALLS.md`。

### 报错"对端提前关闭"

服务端把连接关了。常见原因：keep-alive 没实现（每个请求回完就关），
或者空闲超时设得太短（客户端还没来得及发下一个请求就被踢了）。
用 `--conns 1 --requests 10 -v` 这种小规模复现，配合服务端日志看。

### QPS 上不去，但服务端 CPU 也没跑满

按顺序排查：

1. 客户端 CPU 是不是满了？（看报告里的 CPU 提示）→ 多开几个客户端进程
2. 连接数是不是太少？`--conns 10` 打不出高吞吐，先加到几百上千
3. 有没有开 pipeline？`--pipeline 16` 通常能明显提高吞吐
4. 用 `perf top` 看服务端到底卡在哪个函数上（这是 M6 要交的火焰图）

## 9. 做对照实验的标准流程

M6 的产出是"优化前 → 优化后"的对比表，做法是**一次只改一个变量**：

```bash
# 1. 先测一个基线，写清楚环境
./build/echo_bench --conns 1000 --requests 1000 --label baseline \
                   --json docs/bench/baseline.json

# 2. 只改一个地方（比如服务端从 1 线程改成 4 线程），再测一遍
./build/echo_bench --conns 1000 --requests 1000 --label 4thread \
                   --json docs/bench/4thread.json

# 3. 两轮的差别就是"这一个改动"带来的，把两边数字抄进 docs/RESULTS.md
```

值得做的对照（都在 M6 的计划里）：

| 变量 | 怎么测 | 想验证什么 |
|---|---|---|
| 线程数 | 服务端 1 线程 vs 4 线程 | 多线程到底有没有用、扩展性是不是线性的 |
| Nagle 算法 | 加不加 `--nodelay` | 小包场景 Nagle 有没有拖慢响应 |
| 内存池 | 代码里开关内存池，各测一遍 | 内存池省下了多少时间（配合火焰图看 malloc 占比） |
| ET vs LT | 服务端切换触发模式 | 两种模式的吞吐和 CPU 占用差多少 |
| pipeline | `--pipeline 1` vs `16` | RTT 对吞吐的影响有多大 |

每轮测**至少 3 次**，取中位数——单次结果抖 10% 是常事，
只测一次就下结论，很容易把"随机波动"当成"优化见效"。

## 第一部分：这个项目到底在干什么，为谁服务

### 先看它给谁用

短链服务，就是把很长的网址变短：

```
原始：https://news.example.com/2026/09/14/huawei-campus-recruit?id=88213&from=wechat
短链：http://你的域名/aB3c
```

别人点开 `http://你的域名/aB3c`，你的服务器看一眼 `aB3c`，立刻告诉浏览器
"去那个长网址"，浏览器就跳过去了。就这么简单。

**真实世界里谁在用**：新浪微博的 `t.cn`、B 站的 `b23.tv`、Twitter 的 `t.co`。
用途是四件事——短信里省字数（一条短信 70 字）、二维码更简单更好扫、
运营能统计"这个链接被点了多少次、谁点的"、绕开某些平台对长链接的屏蔽。

### 但你要知道：面试官其实不在乎短链

短链只是一个"挂在你服务器上的业务噱头"。华为面试官真正想看的是：
**你这台服务器是怎么造出来的，能同时接住多少人。**

所以他不会问"短链怎么实现的"，他会问：
- "1 万个人同时连上来，你的服务会怎样？"（→ 你的 epoll + 线程模型）
- "内存会不会一直涨？"（→ 你的内存池和连接回收）
- "一个客户端连上来只发一半数据就不发了，你能撑多久？"（→ 你的定时器）
- "这些数字你怎么知道的？"（→ 你的压测报告）

短链就 200 行代码，服务器框架才是 3000 行的那部分。别搞反了重点。

### 做完之后，它能"为别人服务"的三层

1. **最直接的一层**：你把它部署到一台云服务器（学生机 10 块钱一个月）+ 买个便宜域名，
   它就是一个**别人真的能用的网站**——任何人用你的短链，浏览器里能跳转。
   简历上这一条从"本地能跑"变成"线上可访问"，价值差好几倍。
2. **中间层**：你写的是一块"地基"。nginx、Redis、gRPC 都是这种地基。
   公司里每个后端系统都建在这种地基上。会造地基的人，进的是核心组。
3. **对你个人**：面试时你脑子里有真实数字（QPS、P99 延迟、内存曲线、火焰图），
   这是背八股的人编不出来的东西。这是你和别人拉开差距的地方。

## 第三部分：第 0 天 —— 装环境（半天）

### 1. 装 WSL2（在 Windows 的 PowerShell 里执行，要管理员）

开始菜单搜 `PowerShell` → 右键 → **以管理员身份运行**，然后：

```powershell
wsl --install -d Ubuntu
```

- 会下载几分钟，然后**要求重启电脑**。重启。
- 重启后自动弹出 Ubuntu 窗口，让你设用户名和密码。
  **用户名用小写英文**（比如 `dev`），不要用中文或大写；密码输入时不显示字符，是正常的。
- 之后想再进 Ubuntu：开始菜单搜 "Ubuntu"，或 PowerShell 里敲 `wsl`。

**常见报错**：如果提示"虚拟化未启用"，进 BIOS 打开 `Intel VT-x` / `AMD-V`；
如果 `wsl --install` 报组件未安装，先执行 `wsl --install --no-distribution` 再重试。

### 2. 装开发工具（在 Ubuntu 窗口里执行）

项目已经在 Windows 桌面了，先搬进 Linux 家目录（**不要留在 /mnt/c 里**，IO 慢很多倍）：

```bash
mkdir -p ~/projects
cp -r /mnt/c/Users/32031/Desktop/mini-net ~/projects/mini-net
cd ~/projects/mini-net
ls                      # 应该看到 CMakeLists.txt include src tests docs
bash scripts/env-setup.sh
```

`env-setup.sh` 会装 g++ / cmake / gdb / valgrind / perf / netcat，最后打印每个工具是否就绪。

### 3. 第一次构建 —— 这是你今天的验收

```bash
cd ~/projects/mini-net
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure
```

预期：编译通过，测试输出 `100% tests passed`（骨架里的 Buffer 和定时器已经能用了）。
**看到这行字，你的环境就合格了，今天可以收工。**

顺手装个 VS Code：Windows 里装 VS Code，再装扩展 `WSL`，
然后在 Ubuntu 里敲 `code ~/projects/mini-net`，就能在图形界面里看代码了。

## 第四部分：第 1 周 —— 每天 1.5 小时，做出你的第一个服务器

每天固定的收尾动作：`git add -A && git commit -m "..."`，
提交信息写"为什么这么改"，不写"改了啥"（面试官真的会翻 commit 记录）。

### Day 1（1.5h）：先读懂骨架，别急着写

打开 `include/mini_net/` 里 4 个头文件：`EventLoop.h` `EpollPoller.h` `Channel.h` `TcpServer.h`。

用纸画出这四个类的关系：
- `EventLoop` 是"心脏"，它不停转圈问操作系统"哪个 fd 有动静了"；
- `EpollPoller` 是"问操作系统"的那只手（epoll 的封装）；
- `Channel` 是"一根管道的档案"：fd + 关注什么事件 + 有事件了叫谁；
- `TcpServer` 是"门卫 + 花名册"：听端口、接受新连接、管理现有连接。

**产出**：在 `docs/ARCHITECTURE.md` 里用文字或 mermaid 画一版你自己的理解。
画错很正常，写完代码再回来改一遍，这就是你的面试讲解稿。

### Day 2（2h）：写 `EpollPoller`

顺序不要变：先构造/析构 → 再 `updateChannel` → 最后 `wait`。

- 构造：`epoll_create1(EPOLL_CLOEXEC)`；析构：`close(epfd_)`
- `updateChannel`：如果这个 fd 第一次加，用 `EPOLL_CTL_ADD`，否则 `EPOLL_CTL_MOD`
  （判断依据是 `ch->in_poller_`，所以你要在 Channel 里维护这个标志）
- `wait`：`epoll_wait(epfd_, events_.data(), kMaxEvents, timeout_ms)`，
  把就绪的 fd 对应的 `Channel*` 塞进 `active`，返回数量

现在你可以正式改 `CMakeLists.txt` 了：把 `src/EpollPoller.cc` `src/Channel.cc` `src/EventLoop.cc`
加进 `add_library(mininet STATIC ...)` 里（注释里已经写了规矩）。

**查手册**：Ubuntu 里敲 `man epoll`，或者 `man 2 epoll_wait`。别只搜博客。
**验收**：编译通过；写个临时 main 只创建再销毁 poller，跑 `cmake -B build-asan -DENABLE_ASAN=ON` 无报错。

### Day 3（2h）：写 `Channel::handleEvent` 和 `EventLoop::loop`

- `Channel`：`enableReading()` 把 `events_` 或上 `EPOLLIN`（用 `EPOLLET` 就是边缘触发），
  再通知 poller 更新；`handleEvent(revents)` 根据 revents 分别调读/写/关闭回调。
  **必须在阻塞的 `accept`/`read`/`write` 之前**把 fd 设成非阻塞（`fcntl(fd, F_SETFL, O_NONBLOCK)`）。
- `EventLoop::loop`：`while (!quit_) { active_.clear(); int n = poller_->wait(active_, -1);
  for (auto* ch : active_) ch->handleEvent(ch->revents()); }`

**坑**：`epoll_wait` 返回的 `active` 里可能有已经被关闭的 Channel（悬垂指针），
M1 阶段先保证"连接关闭时从 poller 里摘掉再析构"。

### Day 4（2h）：写 `TcpServer`，让它真的跑起来

`socket()` → `bind()` → `listen()` → 设非阻塞 → 包成 `Channel` 关注 `EPOLLIN`；
`handleAccept()` 里**循环 `accept()` 直到返回 -1 且 errno == EAGAIN**（只调一次是最经典的 bug）。
每个新连接建一个 `Channel`，收到数据就回写（回显）。

然后把 `src/main.cc` 里注释掉的几行打开，跑起来：

```bash
cmake --build build -j && ./build/mini_net_server 8080
```
另开一个终端：
```bash
nc 127.0.0.1 8080        # 然后随便打字回车，看到原样返回就成功了
```

### Day 5（2h）：跑验收 + 记坑

直接跑我给你写的验收脚本：

```bash
cd ~/projects/mini-net && bash scripts/smoke_test.sh 8080
```
它会自动：启动服务 → 回显测试 → 记录 fd 基线 → 拉 1000 个并发连接 → 检查 fd 有没有回收 → 关服务。
把每一行结果和数字抄进 `docs/RESULTS.md`。

再补两个必修坑，都写进 `docs/PITFALLS.md`：
1. 对端关闭后你继续 `write` 会被 SIGPIPE 直接杀掉进程 —— 用 `send(..., MSG_NOSIGNAL)` 或忽略该信号；
2. 所有系统调用都要处理 `EINTR`（被信号打断，应该重试而不是当错误）。

**第 1 周结束你应该能说**：我写了一个单线程 epoll 服务器，1000 并发连接下 fd 无泄漏，
ASAN 干净，QPS 是 X，这是它的代码和踩坑记录。—— 这句话已经可以写进简历了。

## 第五部分：卡住了怎么办（小白必备）

**三板斧，从便宜到贵**：
1. **读报错的第一行**。编译器和链接器都会告诉你 `文件:行号: 错误内容`。
   看不懂英文就复制那一行去搜（但要看中文博客的评论，别张嘴就抄答案）。
2. **gdb 看它是怎么死的**：
   ```bash
   gdb ./build/mini_net_server
   (gdb) run 8080
   # 崩了之后：
   (gdb) bt          # backlog：调用栈，告诉你崩在哪一层
   (gdb) print 变量名
   ```
3. **看系统调用**：`strace -f -e trace=network ./build/mini_net_server 8080`，
   另开终端去连它，你会看到每一次 accept/read/write/close。程序"以为自己在干嘛"和
   "实际在干嘛"往往不一样，这一条最能破案。

**ASAN 报错怎么读**：它会用 `^^^^` 指出出错那一行，并说清是读越界、写越界还是 use-after-free。
不要跳过它，ASAN 报的每一个错在面试里都是加分题。

**问问题的模板**（问我或问任何人，用这个格式，回复会快很多）：
> 我想做：___
> 我写了这段代码：___
> 完整报错：___
> 我已经试过：___
> 我猜问题在：___

**三条纪律**：
- 卡住超过 2 小时就换个任务（比如回去读 TCP 那节），别死磕到心态崩。
- 贴网上的代码之前先问自己"这行为什么对"；讲不清就不要留在仓库里。
- 每天必须 commit 一次。哪怕只改了两行，commit 记录本身就是你的成长证明。

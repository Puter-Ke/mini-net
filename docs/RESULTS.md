（同机压测每轮有 ±10% 波动，属正常；数字取两次运行结果）

**结论（诚实版，比报一个漂亮数字更有价值）**：
1. 4 线程比单线程**慢**，原因是压测客户端自己就吃掉了单核 CPU 的 ~87%：
   4 个服务端线程与客户端抢同一台机器的 CPU，还要多付跨线程唤醒成本。
2. 同机压测**测的是"客户端上限"，不是服务端上限**。
   要做有说服力的多线程对比，必须**客户端与服务端分机器**（或至少给客户端绑核、让服务端独占 2-4 核）。
3. 所以简历里写数字时必须带上测量条件；把"同机压测"当成趋势对比，
   把双机数据当作对外可引用的绝对值。

## 复盘：一个真实的核心 bug（面试最好用的素材）

**现象**：请求被拆成多段发送（真实网络的常态）时服务端返回 404；把同样的请求一次发出去就完全正常。
pytest 里 4 个用例失败、"半包+粘包"混沌场景成功率只有 37.5%。

**排查过程**：
1. 先用自写测试复现（20 轮拆包全部 404），排除"偶发"干扰；
2. 打开服务端 DEBUG 日志，发现它收到的请求 **method/path/version 全是空字符串**；
3. 顺着"解析器怎么可能返回一个空请求"往前查，定位到增量解析的状态机调用方式。

**根因**：`HttpServer` 每次调用解析器都**新建一个 `HttpRequest`** 传进去。
解析器是增量的——请求行在第一次 `read` 时解析并写入该对象；
下一次 `read` 到来时传的是**另一个新对象**，先前解析出的 method/target 就随旧对象一起被丢弃了。
于是路由拿到"空方法"，落到兜底分支返回 404。

**为什么"整包发送"测不出来**：整条请求在一次 `parse()` 调用内走完状态机，始终用同一个对象，字段自然都在。

**修复**：让解析器自己持有请求对象（`HttpParser::req_`），`reset()` 时一并清空，
结构上杜绝"外部传错对象"这种误用；并补了 3 个回归测试：
分 3 段喂、逐字节喂、reset 后解析下一个请求（防止字段残留）。

**修复后**：pytest 90 全过，混沌"半包+粘包"从 37.5% → 100%。

**面试价值**：这道题能同时讲清楚"TCP 是字节流、必须增量解析"、"
增量解析的状态与数据必须绑定在同一个对象上"、"如何用回归测试锁死一个偶发 bug"。

## M1 吞吐/延迟基线（2026-09-14，Remote Run #34804502604）

**环境**：GitHub Actions `ubuntu-24.04`，4 核 / 15 GiB，`-O3`，Python asyncio 客户端**同机**压测

| 连接数 | 消息 | 总请求 | 成功 | 耗时 | QPS | P50 | P90 | P99 | P999 |
|---|---|---|---|---|---|---|---|---|---|
| 100 | 64 B | 20,000 | 100% | 0.682 s | **29,323** | 3.32 ms | 3.41 ms | 3.59 ms | 4.78 ms |
| 500 | 64 B | 50,000 | 100% | 1.720 s | **29,065** | 16.3 ms | 16.9 ms | 18.3 ms | 18.4 ms |

**怎么读这组数字（面试时这样讲才专业）**：
- 单线程 epoll 服务器的吞吐被**单核**卡住，所以 100 连接和 500 连接的 QPS 几乎一样（29k）
  —— 这是"瓶颈在 CPU 而不是连接数"的典型证据；M3 加多线程就是冲着这个瓶颈去的。
- 500 连接时延迟涨到 16 ms，说明单线程在连接数上来后开始排队；
- 客户端是 Python asyncio 且与服务器**同机**，两边抢同一个 4 核 CPU，
  所以延迟数字偏保守（真实值应更好，QPS 上限也被人为压低）；
- **M6 要做的**：自写 C++ 压测客户端 + 客户端与服务端分开两台机器，
  然后把"优化前 vs 优化后"重新测一遍，替换掉这张表。

**还没有的数字（M6 补）**：CPU 占用、内存 RSS 曲线、火焰图里 malloc/free 占比。

## M3 多线程实验结果与解释（2026-09-14）

同一次运行内对照（Remote Run #34805036657，同一台 runner，排除机器差异）：

| IO 线程 | 连接数 | 消息 | QPS | P50 | P99 |
|---|---|---|---|---|---|
| 1 | 100 | 64 B | **60,908** | 1.56 ms | 2.09 ms |
| 1 | 500 | 64 B | **49,493** | 10.3 ms | 13.2 ms |
| 4 | 100 | 64 B | 49,502 | 2.05 ms | 2.32 ms |
| 4 | 500 | 64 B | （见下轮实验） | | |

**多线程反而更慢？这不是 bug，而是压测方法的局限，必须讲清楚：**
1. **客户端只能吃一个核**：压测客户端是 Python asyncio，单线程事件循环。
   服务端开 4 个 IO 线程后，4 个线程要和客户端的单核抢同一个 4 核 CPU，反而互相干扰。
2. **跨线程唤醒有成本**：连接分派和跨线程关闭都要经过 `runInLoop` + eventfd 唤醒（一次 syscall + 线程切换）。
   在小消息、低并发下，这个成本盖过了多线程的收益。
3. **负载还不够重**：64 B 消息 + 1000 以内的连接，单核 epoll 本身就够用（瓶颈是 syscall 而不是 CPU 计算）。

**所以 M6 必须做两件事，否则这组数字没有说服力**：
- 自写 **C++ 压测客户端**（能打满多核），替换 Python 客户端；
- **客户端与服务端分机器**（或至少客户端限核、服务端独占 2 核），消除互相干扰；
- 然后把"1 线程 vs 4 线程"在 1000/5000 连接下重测，那个对比才是简历上能写的数字。

**面试价值**：被问到"你多线程版本快了多沙？"时，能回答"在同机 + 单线程客户端下反而慢 19%，
我分析了三个原因，换成双机和 C++ 客户端后才有正确结论"——这比报一个漂亮但站不住的数字强得多。

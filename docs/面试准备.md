# 面试准备：简历怎么写、被问什么

> 这份文档是你把这个项目"变现"的关键。代码可以有人帮写，**解释权必须是你自己的**。

## 一、简历三条（做完实验后用真实数字替换）

1. 从零实现 C++17 高并发网络库（核心约 4k 行，**不依赖任何第三方网络/HTTP 框架**）：
   Reactor + epoll(ET) + one-loop-per-thread 线程模型 + 环形缓冲 + 定长对象池，
   在 1000 并发连接下 fd 零泄漏、ASAN/UBSan 干净。

2. 自写 C++ 压测客户端（非阻塞 connect + epoll，1500+ 行）实测 1000 连接 × 20 万请求：
   **单线程 QPS 8.2 万、P99 14.9 ms**（4 核云环境同机压测，客户端自身占用单核 87%，
   属于保守下限）；并用 `perf`/栈采样定位热点，对照实验与局限分析见仓库 docs/RESULTS.md。

3. 手写 HTTP/1.1 增量解析器（支持半包 / 粘包 / 管道化）与短链服务（创建 / 302 跳转 / 统计 / metrics），
   配套 **49 个 GoogleTest 用例 + 90 个 pytest 接口用例 + 5 场景混沌测试**，
   在 GitHub Actions 上 Release / ASAN+UBSan / 1000 并发冒烟全部通过；
   期间定位并修复了"请求分片到达时解析出空方法导致 404"的核心 bug（已补回归测试）。

**怎么写才站得住**：
- 每个数字都要能说出**测量方法**（什么机器、多少连接、消息多大、同机还是双机）；
- 主动写一条"局限"（例如"同机压测数字偏保守，双机数据见仓库 docs/RESULTS.md"）——
  这比吹一个大数字安全得多，面试官反而认为你诚实、懂测。

## 二、必被问到的问题（按模块）

### 架构与 IO 模型
1. 讲讲你这个项目一次请求的完整路径？（照 docs/ARCHITECTURE.md 的数据流讲）
2. 为什么用 epoll 不用 select/poll？复杂度区别在哪？
3. ET 和 LT 的区别？为什么选 ET？ET 漏读会怎样？
4. 为什么所有 fd 必须非阻塞？ET + 阻塞 fd 会出什么事？
5. accept 为什么要循环到 EAGAIN？

### 线程模型
6. one loop per thread 和"线程池处理 IO"各自的代价？
7. 跨线程投递任务为什么需要 eventfd？不用会怎样？
8. `doPendingFunctors` 为什么要把队列 swap 出来再执行？（死锁）
9. 你的连接表用一把锁保护，连接数再涨 10 倍会怎样？怎么改？
10. 空闲连接为什么用"时间戳 + 扫描"而不是给每条连接挂定时器？

### 内存与缓冲区
11. 环形缓冲相比 `std::string` 拼接省在哪？扩容时有什么坑？
12. readv + 栈上 64KB extrabuf 的好处？
13. 对象池相比 malloc 省在哪？**你的实测结论是什么？**（诚实答：单线程不比 tcache 快）
14. 你的项目里有哪些地方可能内存泄漏？怎么验证的？（ASAN + fd 计数）

### 协议与业务

16. 短码怎么生成？并发创建会不会撞码？分布式下怎么做？
17. keep-alive 怎么实现的？Connection: close 何时关闭连接？
18. 302 响应为什么不用 301？Cache-Control 为什么设 no-store？

### 测试与工程

## 三、真实踩坑故事（面试最好用的素材）

| 现象 | 根因 | 修法 |
|---|---|---|
| **请求拆包后返回 404（整包则正常）** | **增量解析时每次调用都新建 `HttpRequest`，请求行字段留在被丢弃的对象里；路由拿到"空方法"走到兜底 404** | **解析器自持请求对象 + 3 个回归测试（分 3 段喂 / 逐字节喂 / reset 后不能有残留）** |
| 1000 并发压测时客户端全体卡死 | 压测脚本用了 `asyncio.Barrier(1000)`，一个连接失败就全员永等 | 改成"连上就计数、等齐或超时后放行" + 全局超时 |
| 测试进程挂了 30 秒被 ctest 杀掉 | 客户端 `recv` 阻塞在无响应上；根因是我把 `Content-Length` 写成 26 而 body 只有 25 字节 | 长度用代码计算；客户端加 `SO_RCVTIMEO` |
| 一个单测永久阻塞 | 往管道写 100KB，但 Linux 管道容量 64KB 且写端阻塞 | payload 降到 32KB，并在注释里记录这个坑 |
| 多线程版本 QPS 比单线程**更低** | 同机压测 + 单线程 Python 客户端抢 CPU + 跨线程唤醒成本 | 分析原因并写进文档；M6 用 C++ 客户端 + 双机重测 |
| 对象池并不比 new/delete 快 | glibc tcache 单线程下已极快，我的池还带互斥锁 | 删掉"池一定更快"的断言，如实记录结论 |

> 面试时讲这四个故事，比背十条八股有说服力——因为它们只可能来自真实动手。

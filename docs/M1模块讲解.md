## 一、一次回显请求的完整路径（先把这条线记住）

```
客户端张三：connect 到 8080
   │
   ├─1─ 你的 listen_fd 上有 EPOLLIN 事件
   │     epoll_wait 返回 → Channel(listen_fd)::handleEvent → read_cb_ → TcpServer::handleAccept()
   │
   ├─2─ accept4() 循环直到 EAGAIN，拿到新 fd = 7（SOCK_NONBLOCK）
   │     给 fd=7 建一个 Conn{ Channel, Buffer }，注册 read/close 回调
   │     把 fd=7 的 Channel 加到 epoll（enableReading → EPOLL_CTL_ADD）
   │
   ├─3─ 张三发来 "hello"
   │     epoll_wait 返回 fd=7 可读 → Channel::handleEvent(EPOLLIN) → TcpServer::handleReadable(7)
   │
   ├─4─ Buffer::readFd() 把字节读进缓冲区，on_message_ 回调被调用
   │     main.cc 里的业务代码：send(fd, data, len, MSG_NOSIGNAL) 原样发回
   │
   ├─5─ ET 模式必须继续读到 EAGAIN 才算读干净（while 循环里 continue）
   │
   └─6─ 张三关闭连接：readFd 返回 0 → closeConn(7)
         顺序：从 conns_ 摘除 → channel.disableAll()（EPOLL_CTL_DEL）→ close(7)
```

**面试第一问通常是"讲讲你这个服务端怎么处理一个请求的"**，
照着上面这 6 步讲，每一层都能展开，这就是好答案。

## 二、每个类为什么存在（职责边界就是面试考点）

| 类 | 一句话职责 | 为什么单独拆出来 |
|---|---|---|
| `EventLoop` | 不停地问系统"谁有动静了"，然后派发 | 一个线程一个循环（one loop per thread），IO 和线程绑定，几乎不用锁 |
| `EpollPoller` | epoll 的薄封装：注册/修改/等待 | 把 epoll API 隔离开，将来换 io_uring 只改这一个文件 |
| `Channel` | 一个 fd 的档案：关注什么事件 + 事件来了叫谁 | 一个 fd 可能有多种状态（可读/可写/关闭），用回调拆开 |
| `TcpServer` | 门卫（listen/accept）+ 花名册（连接表） | 连接的生命周期管理独立于 IO 机制 |
| `Buffer` | 应用层缓冲区，解决粘包/拆包 | TCP 是字节流，没有消息边界，必须自己缓存 |
| `Conn`（私有结构） | 一条连接的落地点：fd + Channel + 缓冲 | "连接"是状态，光有 fd 不够 |

## 三、12 个必被问到的问题（含答案要点）

**1. 为什么用 epoll，不用 select/poll？**
select/poll 每次调用都要把全部 fd 拷进内核并线性扫描，复杂度 O(n)，且有 1024 fd 上限。
epoll 用红黑树管理 fd（增删 O(log n)）、就绪链表返回（只把有事件的 fd 给你），
拷贝只发生在 epoll_ctl 时，所以适合海量连接。

**2. ET（边缘触发）和 LT（水平触发）的区别？为什么你选 ET？**
LT：只要缓冲区还有数据，每次 epoll_wait 都会通知你 —— 写起来简单，但通知次数多。
ET：只在状态**变化**时通知一次 —— 通知少、syscall 少，但你必须一次把数据读干净（循环到 EAGAIN），
漏读会导致连接"卡死"再也不通知。本项目选 ET，代价就是第 4 步那个 while 循环。

**3. 为什么 fd 必须是非阻塞的？**
ET + 阻塞 fd 是致命组合：循环 read 到最后一次会**阻塞住整个线程**，
这一个慢连接就把所有其他连接全卡死。所以 `socket/accept4` 都带 `SOCK_NONBLOCK`。
（M1 里的 `accept4(..., SOCK_NONBLOCK|SOCK_CLOEXEC)` 就是这个原因。）

**4. 为什么 accept 要循环到 EAGAIN？**
ET 模式下"来新连接"只通知一次。如果你只 accept 一次，
剩下的连接就留在内核半连接/全连接队列里，直到下一个新连接到来才可能被处理 ——
表现为"客户端连不上/超时"。这是新手最经典的 bug。

**5. EINTR 是什么，为什么要重试？**
你的进程收到信号时，阻塞中的系统调用会被打断并返回 -1、errno=EINTR。
这不是错误，应该 `continue` 重试。我在 `epoll_wait`、`accept4`、`read` 三处都处理了。

**6. 为什么开头要 `signal(SIGPIPE, SIG_IGN)`？**
对端已经关闭，你继续 write/send，内核会给你发 SIGPIPE，默认动作是**直接杀掉进程**。
所以要么忽略这个信号，要么用 `MSG_NOSIGNAL`。我两个都做了（双保险）。

**7. 粘包/拆包是怎么回事？**
TCP 是字节流，"两次 send" 和 "一次 read" 之间没有对应关系：
你一次 read 可能拿到半个请求，也可能拿到两个半请求。所以需要 `Buffer` 做缓存，
再用协议解析器（HTTP 用 `\r\n\r\n` + Content-Length）切出完整消息。M5 会实现。

**8. Channel 析构时为什么必须先 `disableAll()`？**
epoll 内部保存的是 `event.data.ptr`，也就是 `Channel*`。
如果 Channel 释放了但 epoll 里还留着这个指针，下一次事件返回就是 **use-after-free**，
gdb 里会看到一个莫名其妙的崩溃。所以析构函数第一件事就是从 poller 摘掉自己。

**9. 为什么 `closeConn` 里的顺序是"先摘花名册、再从 poller 摘、最后 close"？**
因为回调链可能重入（比如 close 触发的回调又访问连接表）。
先让 `conns_` 里查不到这条连接，后面的操作就不会重复执行；顺序反了就可能二次 close、
或者对已关闭的 fd 再操作（EBADF）。

**10. `pending_` 队列为什么要在 IO 派发之后执行？**
先处理 IO 保证网络吞吐（延迟敏感），再执行其他线程投递的任务。
另外 `doPendingFunctors` 用了 swap 到一个局部变量再执行 —— 如果把执行放在锁里，
任务里再调用 `queueInLoop` 就会**死锁**。这是非常常见的考点。

**11. 你的服务能扛多少？瓶颈在哪？**
M1 单线程版：瓶颈在**单核 CPU**，QPS 大概几千到几万（取决于机器和消息大小）。
证据是 `perf top` 里 CPU 几乎 100% 且集中在 syscall/你的代码上，
而 `ss -s` 显示连接数才 1000，不是 fd 不够。M3 加多线程就是这个瓶颈的直接解法。

**12. 现在这个版本有什么已知缺陷？（敢承认缺陷是加分项）**
- `send` 没有处理"只写了一半"（返回值 < len 时要加写缓冲 + 关注 EPOLLOUT）；
- `queueInLoop` 还没用 eventfd 唤醒，跨线程任务最多延迟 100ms；
- 单线程，吃不满多核；
- `Buffer` 每次读到 64KB 才扩容，还没有环形复用。
（这正是 M3/M4 要解决的，说出来显得你知道边界在哪。）

## 四、你必须自己动手改的 3 处（不做这 3 处，项目就"不是你的"）

1. **把 `handleAccept()` 里的 accept 循环去掉一次**（只 accept 一个），
   用 `nc` 脚本同时连 50 个，观察有多少连不上 —— 亲眼看到 bug，你才记得住 ET 的坑。
   看完改回来。结果写进 `docs/PITFALLS.md`。
2. **给 `main.cc` 加一个统计接口**：自己设计一个简单协议，
   比如客户端发 `STATS\r\n`，服务端回 `conns=3 recv=1024\r\n`。
   这逼你理解 `on_message_` 回调拿到的数据可能是半个请求（体会粘包）。
3. **给 `send` 加写缓冲**：当 `send` 返回值 < len 时，把剩余数据存到 `Conn` 的写缓冲，
   关注 `EPOLLOUT`，可写时继续发。做完你就真的懂了非阻塞写。
